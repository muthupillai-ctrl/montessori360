Taji — Internal Scope & Technical Architecture

Audience: internal engineers. The public version is at ahamsys.com/taji/architecture.html. Status: reflects the code as of 2026-09-26. Covers both products: Taji One (the Student Information System, called SIS below) and Taji AMS (the Academic Management System, AMS below). Code, packages and containers still use the earlier internal name montessori360.

1. Purpose and scope

Taji is a multi-tenant SaaS platform for schools, preschools and early-learning institutions. The SIS runs school administration and the parent relationship; the AMS runs curriculum, child progress and teaching material. They are separate applications with separate databases, joined by single sign-on and a server-to-server API, so a school can adopt one or both.

One TypeScript monorepo (npm workspaces). Each API is Node.js 22 with Express 5 and the pg driver, written as ES modules; each frontend is an Angular standalone-component SPA.

4. Multi-tenancy and request pipeline

Each school is a tenant with its own PostgreSQL schema (tenant_<code>) in the SIS database, and a schema of the same name in the AMS database. Shared tables (tenants, plans, platform admins, API keys, AI usage) live in public. New SIS schemas are created from a template procedure (create_tenant_schema()); AMS schemas are provisioned on first use.

flowchart LR
    R[HTTP request] --> SEC[helmet, CORS, rate limit 200/min per IP]
    SEC --> P{Route}
    P -- /auth, /platform, /health --> C1[Public or platform handlers]
    P -- all other /api/v1 --> JWT[JWT verify]
    JWT --> T[Tenant schema taken from signed token claim]
    T --> RB[Role check per route]
    RB --> C[Controller / service]
    C --> Q[(Queries scoped to tenant schema)]
  • The school is identified at login, by school code or by subdomain ({code}.ahamsys.com; the login page detects it). The tenant schema is embedded in the signed JWT, so no per-request lookup is needed and it cannot be switched by the client.
  • Platform-admin tokens are separate and only accepted on /platform routes.
  • The AMS runs provisionTenant() on each authenticated request: it creates the schema if missing, applies every table with IF NOT EXISTS and seeds the default curriculum once. Schema changes therefore roll out without a separate migration step.

Design principles

  • Isolation by schema. A query can only reach the schema named in the caller's token.
  • AMS never copies SIS master data. Students and classes are read live from the SIS, so there is one source of truth.
  • Curriculum is data. Areas, activities, levels and prerequisites are editable per school, seeded from a default Montessori curriculum.

6. SIS–AMS integration

6.1 Single sign-on

sequenceDiagram
    actor T as Teacher
    participant SW as SIS web
    participant AW as AMS web
    participant AA as AMS API
    participant SA as SIS API
    T->>SW: click "AMS" in the menu
    SW->>AW: open /sso with the current session token
    AW->>AW: store token, strip it from the URL and history
    AW->>AA: API calls with Bearer token
    AA->>AA: verify JWT with the shared signing secret
    AA->>AA: provision tenant schema if needed
    AA-->>AW: data for the teacher's school

Both APIs share the JWT access-token secret, so a token issued by the SIS is valid in the AMS for the same school and roles. AMS login and token refresh are delegated to the SIS auth endpoints.

6.2 Reading SIS data

The AMS sis-proxy module forwards the caller's token to the SIS for /students, /classes and /subjects. Access rules are therefore always the SIS's own.

6.3 External API keys

School admins create and revoke API keys in the SIS. Keys are stored hashed with the owning tenant schema, and calls authenticate with the X-Api-Key header.

7. AI features

ProductFeatureHow it works
SISNightly insightsScheduled job at 02:00 per school: detects sudden attendance drops, chronic absenteeism and fee-default risk (days overdue, prior late and partial payments). Insights have a severity and are resolved by staff.
SISJournal note assistDrafts a 3–5 sentence teacher's note for a child's daily journal from mood and activities. The teacher edits before publishing.
AMSContent generationGenerates worksheets, lesson plans and question papers from subject, level, topic and constraints (marks, difficulty, question types) as editable HTML drafts.
BothUsage meteringEvery AI call logs input and output tokens and cost against the school and feature in a shared table, visible to the school and the platform admin.

Model: Anthropic Claude via the official SDK. AI output is always a draft for a person to review; nothing is published or sent automatically.

9. Security model

ConcernControl
Cross-school accessSchema per school; schema taken only from the signed token
AuthenticationShort-lived JWT access tokens (15 min) with refresh tokens (7 days); bcrypt password hashes; email reset links
AuthorisationRole checks on every route; parent routes limited to the parent's own children
Platform separationPlatform-admin tokens only valid on /platform routes
AbuseGlobal rate limit (200 requests/min per IP), helmet security headers, CORS allow-list, request-size limits
InputRequest validation with zod and express-validator schemas
Integration keysHashed at rest, revocable, scoped to one school
SSO token handlingToken removed from the URL and browser history immediately on arrival
TransportHTTPS at the edge; databases over TLS
SecretsEnvironment files on the server only, never in source control

Known weaknesses: no MFA, AMS uploads stored on local disk, and a shared signing secret between SIS and AMS (rotation must be coordinated).

11. Frontend architecture

  • Angular standalone components with lazy-loaded routes; an HTTP interceptor attaches the bearer token and refreshes it on expiry.
  • SIS route areas: /login, staff areas (dashboard, students, attendance, fees, classes, timetable, journal, homework, observations, reports, calendar, staff, transport, communication, parents, academic years, AI insights, integration), /parent/* portal, /driver view and /platform/* console.
  • AMS route areas: worksheets, lesson plans, question papers, curriculum, progress, assignments, AI insights and /sso.
  • Both SPAs call their API on the same origin (/api/v1), so no cross-origin requests are needed in production.

12. Deployment and operations

flowchart LR
    U[Browser] -->|HTTPS| EDGE[CDN / TLS edge]
    EDGE --> RP[Nginx reverse proxy]
    RP -->|static| W1[SIS SPA files]
    RP -->|static| W2[AMS SPA files]
    RP -->|/api| C1[SIS API container]
    RP -->|/api| C2[AMS API container]
    C1 --> RD[(Redis container)]
    C1 --> PG1[(Managed PostgreSQL - SIS)]
    C2 --> PG2[(Managed PostgreSQL - AMS)]
    C2 -->|internal network| C1
  • APIs run as Docker containers from one Compose file; Nginx serves the Angular builds and routes /api by hostname. Proxy upstreams resolve through Docker DNS at request time, so a stopped API cannot prevent the proxy from starting.
  • Portable by design: any Linux host with Docker, on our infrastructure, the client's cloud or on-premise. PostgreSQL 17 is managed; Redis runs alongside the APIs.
  • Deploys are scripted: build locally, sync artefacts, rebuild the container, wait for /health. SIS schema changes use versioned migrations; AMS schemas update themselves on first request, or all at once with a provisioning script.
  • Configuration is per-service environment files; the APIs are stateless apart from AMS uploads.

13. Roadmap and open decisions

  1. Online fee payments (Razorpay checkout and webhooks) from the parent portal.
  2. RFID reader endpoint for tap-to-mark attendance and bus boarding (firmware ready).
  3. Push notifications and native mobile apps for parents and drivers.
  4. Live bus location for parents.
  5. MFA for staff; per-service signing keys instead of a shared SSO secret.
  6. Object storage for AMS uploads.
  7. Deeper SIS–AMS links: AMS mastery feeding SIS progress cards automatically.
  8. Self-service school onboarding and subscription billing.
